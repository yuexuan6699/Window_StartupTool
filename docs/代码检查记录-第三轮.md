- **需求**：开机登录自动拉起控制端时，只驻留托盘，不弹出主窗口。
- **实现**（三段）：`Program` 解析 `--minimized`/`--tray` → `App.StartMinimized` → `MainWindow` 构造期 `Opacity=0` + `ShowInTaskbar=false`（首帧不可见），`Window_Loaded` 用 `DispatcherPriority.Loaded` 延迟到托盘图标建好后再 `Hide()` 并复位两项；`RestoreFromTray()` 显示前同样复位；`ServiceInstaller.TrySetClientAutoRun` 写 Run 值改为 `"<exe>" --minimized`。
- **坑（勿回退）**：`tb:TaskbarIcon` 定义在 `MainWindow.xaml` 的可视树里，**不能在 `Show()` 之前就把窗口 Hide/不 Show**——否则托盘图标不会被创建、用户再也唤不出窗口。必须走"先 Show 装载、Loaded 后 Hide"这条路；同时用 `Opacity=0` + `ShowInTaskbar=false` 抑制闪现。
- **验证**：Debug 与安装版各一轮——`--minimized` 启动后进程存活、`EnumWindows` 可见窗口数 **0**；随后无参再启动一次，单例唤出主窗口、第二实例自行退出；HKLM Run 已带 `--minimized`。

### F11c 脚本「无法启动」

- **现象**：`win-mcp` 点启动后表现为启动不了；服务日志 00:33–03:41 连续 60+ 条「心跳超时（90 秒未收到心跳），将重启」。
- **根因（两条叠加）**：
  1. 该脚本配置 `runInSystemSession=true`（勾选了「在服务会话（Session 0）中运行」）。Session 0 **无交互桌面**，脚本输出日志里是 `RuntimeError: No active interactive desktop for physical input control` → 退出码 1。
  2. 同时 `heartbeatEnabled=true`，但 `.bat` **没有任何 `--beat` 调用**；批处理末尾的 `pause` 让 cmd/python 一直存活（不会以失败退出），于是每 90 秒被服务端按"心跳超时"杀掉重启，形成死循环。
- **处置**：将该脚本改为 `runInSystemSession=false` + `heartbeatEnabled=false`（配置落在 `config\scripts.json`，服务端热重载生效）。
- **验证**：点「启动」→ 状态 `运行中`、PID 有效、会话 1；`0.0.0.0:15692` 监听成功，MCP 端点空 GET 返回 406（正常）；服务重启后自动拉起（约 17 秒就绪）。进程链 `cmd → python → python` 仅一组，无重复实例。
- **后续建议（未改码）**：若确需心跳，必须在该脚本里按《脚本心跳包发送要求》定期调用 `StartupTool.exe --beat <令牌> <Unix秒>`，否则不要开「启用应用层心跳」；同理，GUI/桌面类脚本不要勾「在服务会话（Session 0）中运行」。

## 十四、F12 追记（2026-10-21）：托盘应用图标 / Python 脚本 / 虚拟环境解释器

### F12a 托盘图标不是应用图标

- **现象**：托盘区显示的是蓝底白色播放三角，与 exe 图标（`app.ico`）不一致。
- **根因**：`MainWindow.xaml` 中 `tb:TaskbarIcon.IconSource="{StaticResource TrayIconSource}"` 指向一段**硬编码矢量图**（`DrawingImage`），从未读取 `app.ico`。而 `app.ico` 当时只配了 `<ApplicationIcon>`，该属性仅写入 PE 资源（影响资源管理器/快捷方式），**不会**让 WPF 在运行时通过 `pack://` 取到。
- **修复**：① csproj 增 `<Resource Include="Resources\app.ico" />`；② `Window_Loaded` 调 `ApplyTrayIconFromAppIcon()`：`Application.GetResourceStream(pack://application:,,,/Resources/app.ico)` → `IconBitmapDecoder` → 取 `PixelWidth` 最大帧 → `Tray.IconSource`；③ 保留 XAML 矢量图作兜底，整段 try/catch 静默。
- **为什么不引 `System.Drawing.Common`**：`IconBitmapDecoder` 是 WPF 原生 ico 解码器（支持多帧），无需新增依赖；`BitmapImage` 对 `.ico` 解码不可靠，不采用。
- **验证**：App 编译 0 警告 0 错误；兜底路径保证资源读取失败时托盘仍有图标（这也是 `--minimized` 登录自启场景的硬要求——托盘是唯一入口）。

### F12b `.py/.pyw` 落入默认分支导致必然启动失败

- **根因**：`CommandLineBuilder.Build` 的 `switch` 只有 `.ps1` 与 `.bat/.cmd` 分支，`.py` 走 `_ => new LaunchCommand(ResolveExecutable(path), userArgs)` → `ProcessLauncher` 以 `lpApplicationName = 脚本路径` 调 `CreateProcess`。Windows **不把 `.py` 视为可执行格式**（未装 Python 时连关联都没有），必然失败。
- **修复**：新增 `.py`/`.pyw` 分支，解释器由 `ResolvePythonInterpreter(script.PythonExecutable)` 解析；参数串 `JoinArgs(Quote(path), userArgs)`。
- **验证**：`Py脚本_使用Python启动器`、`Pyw脚本_同样走Python启动器` 两例通过（断言以 `py.exe`/`python.exe` 结尾且脚本路径被双引号包裹）。

### F12c 虚拟环境（目录名不固定）

- **需求**：脚本要使用自身目录下的虚拟环境，但 venv 目录名可能是 `.venv`/`venv`/`env`/自定义，无法靠固定命名猜。
- **方案（用户确认：手动指定 → 填 `python.exe` 路径）**：新增 `ScriptConfig.PythonExecutable`；非空时**原样使用**（venv 无需 `activate`，直接调 `Scripts\python.exe` 即用该环境的 site-packages），为空回退 `py.exe` → `python.exe`。
- **审查要点（保留结论）**：
  1. **不静默回退**：指定了但路径不存在时直接失败，不做"找不到就退回系统 Python"。原因是静默回退会让"以为用了 venv、实际用了全局环境"的依赖缺失极难排查；失败会进信息条 + `logs\service\`，可观测。
  2. **只在 Python 分支解析**：`.bat/.cmd/.ps1` 完全忽略该字段（有测试 `非Python脚本_忽略解释器字段` 守护）。
  3. **Trim 一致性**：UI 保存时 `ApplyEditable` Trim 且全空存 `null`；`ResolvePythonInterpreter` 再 Trim 一次，容忍从资源管理器复制带出的首尾空格。
  4. **服务端无需改白名单**：`HandleUpsertScript` 是整对象合并、只保留 `Order`/`HeartbeatToken`，新字段随 JSON 自然落盘；若将来改为服务端权威字段，必须同步加进 `IpcServer` 保留清单（已写入开发文档 §7.6）。
- **验证**：新增 3 例（venv 解释器原样使用 / 空白裁剪 / 非 Python 忽略），`CommandLineTests` **8/8**；全量 `dotnet test` **136 通过 / 137**，唯一失败仍为既有环境依赖 `BeatCommandContractTests.令牌合法但无服务_返回11`（本机真实服务占用默认管道）。
- **本轮无新增风险项**；未做「解释器存在性校验」是有意取舍（venv 可能稍后创建，硬拦会阻止保存），失败信息已足够定位。

### 构建/验证方法备忘

- `dotnet test` 与 `dotnet build` **不要并行**：两者都会写 `src\StartupTool.Core\obj\Debug\net10.0-windows\StartupTool.Core.dll`，并行会报 `CS2012 ... being used by another process`。先测试、再构建（或反之）串行执行即可。
