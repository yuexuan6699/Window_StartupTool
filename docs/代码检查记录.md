## 一、严重（会导致核心目标失效、或需重启服务才能恢复）

### S1 输出重定向的管道句柄不可继承 → 脚本 stdout/stderr 重定向整体失效
- 位置：`src/StartupTool.Core/Processes/ProcessLauncher.cs:101-119`（`NativeMethods.cs:104-113`）
- 事实：`CreatePipe(out readPipe, out writePipe, IntPtr.Zero, 0)` 传 `lpPipeAttributes = NULL`，按 MSDN 语义这样创建的**两个句柄都不可继承**；代码随后只对父端 `readPipe`、`stdinWrite` 调用 `SetHandleInformation(..., HANDLE_FLAG_INHERIT, 0)` 清继承位，**从未**给子端 `writePipe` / `stdinRead` 置继承位。
- 影响：即使 `bInheritHandles = true`，子进程也拿不到这些句柄 → `hStdOutput/hStdError/hStdInput` 在子进程内是无效句柄；脚本写 stdout 报错、日志采集（`BeginReadOutput`）收不到任何输出、`start /b` 类接力再派生因复制句柄失败而异常。这是 A2/B17「采集脚本输出」的关键路径。
- 修法方向：用 `SECURITY_ATTRIBUTES { bInheritHandle = TRUE }` 创建管道，再对父端读端/写端清继承位。

### S2 以用户令牌启动时未设置 `lpDesktop` → 脚本 GUI 落不到用户桌面
- 位置：`ProcessLauncher.cs:79-84`（`LaunchCore` 构造 `STARTUPINFO`）、`ProcessLauncher.cs:47-74`（`LaunchAsUser`）
- 事实：`STARTUPINFO` 只设了 `cb` / `dwFlags = STARTF_USESHOWWINDOW` / `wShowWindow = SW_HIDE`，`lpDesktop` 始终为 null。服务(SYSTEM, Session 0) 调 `CreateProcessAsUser` 且 `lpDesktop = NULL` 时，子进程**继承父进程的窗口站/桌面**（服务的非交互窗口站），而不是用户桌面。
- 影响：这正是双端架构的核心目标（P4/A3「脚本默认在登录用户桌面会话内启动，GUI 可见」）。不设 `winsta0\default`，用户根本看不到脚本界面，等于退化成旧版 Session 0 不可见问题。
- 附带疑点：对 GUI 类脚本同时给了 `STARTF_USESHOWWINDOW + SW_HIDE`，宿主的首个窗口可能被隐藏（取决于框架是否使用 `SW_SHOWDEFAULT`），需真机验证（见待验证 V2）。
- 修法方向：`LaunchAsUser` 路径显式 `si.lpDesktop = @"winsta0\default"`；GUI 脚本不应无条件 `SW_HIDE`。

### S3 状态广播在持锁路径内重复获取同一信号量 → 每次状态变更固定自锁 2 秒
- 位置：`src/StartupTool.Core/Supervision/ScriptSupervisor.cs:56-91`（`BuildSnapshot` 中 `rt.Gate.Wait(2000)`）
- 事实：`EmitState` → `SnapshotOf` → `BuildSnapshot` 的调用点全部位于**已持有该脚本 Gate 的路径**：`390`、`430`（StartUnderLockAsync）、`498`、`521`（WatchLoop）、`569`、`587`（StopUnderLockAsync）、`277`（ResumeGuardAsync）、`608`（TripCircuit，被 Start 失败路径调用）。`SemaphoreSlim` 不可重入，`Wait(2000)` 会自阻塞整整 2 秒后返回 false。
- 影响：每次启动/停止/熔断/崩溃重启都白等 2~4 秒，脚本启停响应严重迟滞；同时广播线程 `BroadcastLoopAsync`（`IpcServer.cs:330`）每次收到 `StatesBroadcast` 都会调 `GetStates()`，若撞上正持锁的脚本，还要再等 2 秒 → 界面状态刷新明显卡顿、并连带拖慢后续事件。
- 修法方向：区分「持锁内构造快照（不取锁）」与「外部查询取锁」两条路径（如 `BuildSnapshotUnsafe` + 公开查询加锁）。

### S4 GPU 实例名解析恒失败 → GPU 占用恒为 null，`MaxGpuPercent` 永不生效
- 位置：`src/StartupTool.Core/Monitoring/ResourceSampler.cs:161-171`（同时 `:167` 注释把 parts[10] 标为「数字」，也是错的）
- 事实：`GPU Engine` 计数器实例名形如 `pid_1234_luid_0x00000000_0x0000A0DE_phys_0_eng_0_engtype_3D`，按 `_` 切分后 `parts[10]` 是 **engtype 记号**（`3D` / `VideoDecode` / `Compute` 等），不是十进制数；`int.TryParse(parts[10], out _)` 恒失败 → `TryParseInstance` 恒返回 false → 所有 GPU 计数器被跳过。
- 影响：`GpuPercent` 永远为 null（界面 N/A）、`MaxGpuPercent` 超限重启永不触发。旧版「GPU 恒为 0」的缺陷换了个形式复现（注释声称已修复，实际未修复）。
- 修法方向：`engType` 改用字符串（或映射枚举）作为聚合键，保留末段原值。

### S5 广播线程与客户端断开竞态 → 事件推送线程永久终止，只能重启服务恢复
- 位置：`src/StartupTool.Core/Ipc/IpcServer.cs:362-381`（`TryWriteAsync`）与 `:166-171`（`HandleClientAsync` 的 finally）
- 事实：`await client.WriteLock.WaitAsync(...)` 写在 `try` **之外**，而客户端断开时 `HandleClientAsync` 的 finally 会 `client.WriteLock.Dispose()`；广播循环此时正对快照里的该客户端调用 `TryWriteAsync` → `ObjectDisposedException` 逃出 `BroadcastLoopAsync`（该 Task 无任何兜底 catch）→ **广播循环直接结束**。
- 影响：之后所有状态推送与告警通知永久停止（服务仍在跑、脚本仍在守护，但界面状态冻结），只能重启服务恢复。偶发但后果严重。
- 修法方向：把 `WaitAsync` 纳入 try/catch（返回 false 即跳过该客户端）；`StopAsync` 后再释放 `WriteLock`（或改用引用计数/取消而非立即 Dispose）。

### S6 读帧无逐帧/闲时超时 → 本地交互用户可占满管道实例，形成拒绝服务
- 位置：`src/StartupTool.Core/Ipc/IpcServer.cs:139-152`（读循环）＋ `PipeFrame.cs:23-39`（`ReadAsync` 只有整体 CancellationToken，无读超时）
- 事实：`HandleClientAsync` 在 `await PipeFrame.ReadAsync(pipe, ct)` 上无限等待；连接后不发帧或只发半个帧头即可永久占住一个连接。服务端实例上限 `MaxAllowedServerInstances`（约 254）。
- 影响：任一本机交互用户（管道 ACL 允许 Interactive 连接）可耗尽实例 → 控制端连不上、`--beat` 心跳失败（被判 11/14），脚本卡死判定随之失效。
- 修法方向：连接级空闲超时（如 60s 无帧即断开并回收实例）；限制单用户并发连接数。

## 二、中等（功能偏差、脆弱点、安全/性能隐患）

### M1 未配置工作目录时用的是「可执行文件」目录 → `.bat/.ps1` 脚本相对路径基准错误
- 位置：`ProcessLauncher.cs:164-167`（`ResolveWorkingDirectory` 取 `Path.GetDirectoryName(options.FileName)`）＋ `CommandLineBuilder.cs:24-33`（FileName 是 powershell.exe / cmd.exe）＋ `ScriptConfig.cs:33`（文档写明「为空则取脚本所在目录」）
- 影响：`.bat/.cmd` 的 CWD 变成 `C:\Windows\System32`、`.ps1` 变成 `WindowsPowerShell\v1.0`，脚本内相对路径全部解析错误。

### M2 配置 ACL 只施加于文件、未施加于目录，且失败被静默吞掉
- 位置：`ConfigFileSecurity.cs:11-33`（只 catch `UnauthorizedAccessException` 且无日志）＋ `ConfigService.cs:291-322`（`Directory.CreateDirectory` 用默认继承 ACL；`Protect` 只对 tmp 与目标文件调用）
- 影响：`config` 目录未被收紧，非管理员可能删除/替换 `scripts.json`（含心跳令牌）；非提权调试时保护静默不生效，调用方误以为已保护。`.bak` 是否继承旧 ACL 需真机确认（见 V3）。

### M3 管道 ACL 给 Interactive 授予 `CreateNewInstance`，权限过大
- 位置：`PipeSecurityFactory.cs:21-24`（`NativeMethods` 对应 `FILE_CREATE_PIPE_INSTANCE`）
- 影响：控制端作为客户端只需 ReadWrite；额外授予创建实例后，任意交互用户可自建同名管道实例（抢占/仿冒服务端）→ 可伪造响应、截获控制端命令。

### M4 心跳令牌比较非固定时间
- 位置：`ConfigService.cs:104-113`（`string.Equals(..., StringComparison.Ordinal)`）
- 影响：本地管道、窗口极小，风险低，但属于应修的安全细节（应用固定时间比较）。

### M5 v1→v2 迁移的原子写失败会让构造直接抛异常
- 位置：`ConfigService.cs:41-45`（`AtomicWrite` 无 try/catch）＋ `SupervisionWorker.cs:30`（`new ConfigService()` 在服务启动路径）
- 影响：只读/占用/权限不足时抛异常 → **服务与 WPF 控制端启动直接失败**；而「读取损坏」路径已有 B1 保护，写入路径没有同等兜底。

### M6 配置不去重 Id → 重复 Id 会让整轮资源巡检静默失效
- 位置：`ConfigService.cs:268-288`（`Normalize` 不检查重复 Id）＋ `ResourceMonitor.cs:41-42`（`ToDictionary(s => s.Id)` 抛 `ArgumentException`，被 `:91-94` 外层 catch 吞掉）
- 影响：手改配置造成 Id 重复时，CPU/内存/GPU 超限判定与重启全部静默停止（无任何日志）。

### M7 `IsProcessAlive` 把「打不开句柄」当作「已退出」
- 位置：`JobObject.cs:136-141`（`IsProcessAlive`）＋ `JobObject.cs:109-110`（据此过滤 PID）＋ 与 `ScriptSupervisor.cs:629-634`「查询失败=未知，绝不误判 Job 空」的约定矛盾
- 影响：受保护/权限受限的存活进程被过滤掉 → `GetProcessIds()` 少报甚至为空 → 可能进入「Job 已空」判定并触发重启/清理路径（WatchLoop 的双周期复查只降低概率，不消除）。

### M8 `RestartAsync` 无条件清除「用户停止」意图，会复活用户刚停止的脚本
- 位置：`ScriptSupervisor.cs:216-258`（`:228` 置 `UserIntendedStop = false`；未运行分支同样会走 `StartUnderLockAsync(..., isRestart:false)` 启动）
- 影响：`254` 行的守卫只在「延时窗内按停止」时有效；用户按了停止后，若资源/心跳触发的 `RestartAsync` 或界面「重启」到达，脚本会被重新拉起 → 与用户意图冲突。

### M9 `Beat` 在脚本未运行时仍返回 Ok，`NotRunning` 成了死分支
- 位置：`ScriptSupervisor.cs:286-309`（两条分支都 `return BeatResult.Ok`）＋ `ScriptState.cs:39`（`NotRunning` 枚举）＋ `IpcServer.cs:297-298`（`notRunning` 应答分支永不触发）
- 影响：脚本无法区分「心跳被接收并生效」与「心跳被丢弃（脚本已停/已熔断）」，`--beat` 退出码语义随之失真。

### M10 资源巡检对每个脚本各做一次全量 WMI 枚举
- 位置：`ResourceMonitor.cs:47-84`（`:69` 在脚本循环内调 `_externalScanner.Scan(new[] { cfg }, managedPids)`）＋ `ExternalProcessScanner.cs:29-33`（每次新建 `Win32_Process` 全表查询）
- 影响：N 个运行脚本 = 每 5 秒 N 次全表进程枚举，与注释「一次 WMI 批量查询」不符；机器进程多时开销明显。

### M11 外部进程匹配用文件名子串 → 大量误报
- 位置：`ExternalProcessScanner.cs:88-90`（`cmdLine.Contains(fileName)`，只要长度 > 3）
- 影响：`node.exe` / `python.exe` 等同名外部进程会大面积误报，展示统计失真，并会误导后续「用户显式终止」决策（该操作虽需二次确认，但基于错误数据）。

### M12 服务失败恢复策略 `reset= 0` → 重启计数永不归零，恢复只生效一次
- 位置：`ServiceInstaller.cs:137-138`（`failure ... reset= 0 actions= restart/5000/restart/10000/restart/30000`）
- 影响：3 次崩溃后 SCM 不再重启（因为计数不重置），「崩溃自愈」在服务层面实质只生效一轮；应设合理 reset 周期（如 `reset= 86400` 或按需）。

### M13 安装过程的非关键步骤全部静默降级，仍报「安装并启动完成」
- 位置：`ServiceInstaller.cs:31-41`（描述/失败策略/登录自启/启动都走 `RunOptional`，失败仅打印警告，函数仍 `return 0`）＋ `:20-42`（无管理员前置检查）
- 影响：控制端登录自启（HKLM Run）写入失败、服务启动失败都被吞掉，用户看到「完成」实际未生效；非提权运行只靠 sc.exe 退出码兜底。

### M14 `RunSc` 先连续 `ReadToEnd` 两个流再 `WaitForExit` → 经典死锁模式
- 位置：`ServiceInstaller.cs:149-171`（`:164-166`）
- 影响：stderr 写满管道缓冲区时会互相阻塞，`WaitForExit(30s)` 保护形同虚设（sc.exe 输出小，当前风险低，但模式有缺陷，应用异步读取或先 `WaitForExit` 后读）。

### M15 输出读取实为同步阻塞，且固定 UTF-8 解码 → 中文脚本输出乱码
- 位置：`LaunchOptions.cs:32-41`（`:38` `isAsync: false`，注释却称「异步读、避免死锁」）＋ `ScriptSupervisor.cs:611-627`（`ReadLineAsync`）
- 影响：占用线程池线程（长输出时更明显）；中文系统下 cmd/powershell 输出为 GBK/936，按 UTF-8 解码必乱码 → 日志与界面输出不可读（旧版也没解决，属新引入的取舍需确认）。

### M16 帧长度限制只读端生效，写端无上限
- 位置：`PipeFrame.cs:13-21`（写：无校验）vs `:30-31`（读：`> 1MB` 抛错）
- 影响：服务端/客户端写出超长帧（脚本超长输出行、脚本数量激增）时对端判为非法帧并断连 → `AppClientService` 反复重连，界面状态中断。

### M17 事件广播对客户端串行写，单客户端慢会拖垮全体
- 位置：`IpcServer.cs:347-358`（`foreach` 中逐个 `await TryWriteAsync`）＋ `:362-381`（每客户端最长 5s `ClientWriteTimeout`）
- 影响：一个卡住/已断开的客户端每轮最多阻塞 5 秒，其余客户端的状态刷新一起被拖迟（队头阻塞）。

### M18 测试未引用 App 项目 → 单 exe 分流与心跳退出码契约无回归保护
- 位置：`tests/StartupTool.Core.Tests/StartupTool.Core.Tests.csproj:18-21`（只引用 Core/Service）
- 影响：`Program` 多模式分流、`BeatCommand` 的 0/10/11/12/13/14 退出码约定、`ParentConsole` 均零覆盖；约定一旦被改坏无法被测试发现。

### M19 连接失败时管道对象泄漏
- 位置：`IpcClient.cs:36-46`（`ConnectAsync` 中新建的 `NamedPipeClientStream` 在 `ConnectAsync` 抛异常时未 Dispose，`_pipe` 也未被赋值）＋ `AppClientService.cs:52-65`（失败分支只 `client.Dispose()`）
- 影响：服务未运行时每 3 秒重连一次 → 每次失败泄漏一个管道对象/句柄。

### M20 `Process.GetCurrentProcess()` 多处未 Dispose
- 位置：`SessionResolver.cs:35`（`LocalSessionContext.GetActiveSessionId`，5 秒轮询路径）＋ `AppClientService.cs:70`（订阅时）
- 影响：每次调用泄漏一个进程句柄（`Process` 持有的内核句柄直到 GC 终结器才释放）。

### M21 服务关停时逐脚本最长 10 秒等待，可能超出宿主关闭超时
- 位置：`ScriptSupervisor.cs:550-588`（`StopTimeout = 10s` 每脚本）＋ `StopAllAsync`（`ScriptSupervisor.cs:261-265` 串行）＋ `SupervisionWorker.cs:66`
- 影响：脚本多/不响应时，串行停机会远超宿主 `ShutdownTimeout`，进程被强制结束（`KILL_ON_JOB_CLOSE` 能兜底杀进程，但可能来不及写日志/发事件）。需确认宿主超时与脚本数量上限是否匹配（见 V4）。
